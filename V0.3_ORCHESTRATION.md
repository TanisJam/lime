# LIME v0.3 — Orchestration Design Note

**Status:** design, pre-implementation. Targets the goal in the v0.3 brief:
*teach the existing v0.2 composer to orchestrate* — richer output through
contrast, hierarchy and focus, **not** more simultaneous notes.

This note describes how `MusicalRole` and an `OrchestrationDirector` fit the
**current** code, and the smallest migration path that keeps every v0.2 system
and all 118 core tests intact.

---

## 1. What v0.2 actually does today

One bar is composed by `LimeEngine.composeBar(bar)`
(`packages/core/src/engine/LimeEngine.ts`):

```
StateManager.advanceToBar → hostState
FormDirector.at → FormState;  applyForm(hostState, deviation) → effective state
HarmonyPlanner.chordAt(bar), chordAt(bar+1)
PhrasePlanner.at(bar) → PhraseInfo
PhraseDirector.plan(state, phrase) → PhrasePlan      ← last planning step
Orchestrator.composeBar({ …, phrasePlan })
    Arrangement.update(energy) → Set<"pad"|"bass"|"melody"|"percussion">
    for each active voice: generator.generateBar(ctx)  (ctx = BarContext)
    events.sort
```

Two facts matter for v0.3:

1. **"Who plays / how loud / how busy" is decided in three scattered places:**
   - `Arrangement.update(energy)` — a boolean on/off gate per **fixed voice
     name**, keyed on energy alone, with hysteresis.
   - `PhrasePlan` fields `melodicActivity` / `dynamics` / `energy` (arc).
   - Each generator **re-derives its own density** from raw `state` +
     `phrasePlan` thresholds.

   There is no single place that says "this phrase, the ostinato leads and the
   melody rests." That is exactly the gap `OrchestrationDirector` fills.

2. **Everything a generator reads arrives on one object, `BarContext`**
   (`orchestration/BarContext.ts`). Adding a field there reaches all four
   generators with **zero signature churn**. This is the migration lever.

`BarContext` today:

```ts
interface BarContext {
  readonly bar; readonly barStartTick; readonly meter;
  readonly state: MusicalState;
  readonly chord: HarmonicEvent; readonly nextChord?: HarmonicEvent;
  readonly phrase: PhraseInfo; readonly phrasePlan: PhrasePlan;
  readonly rng: SeededRandom;      // per-voice, injected by Orchestrator
}
```

## 2. MusicalRole — the abstraction, mapped onto existing voices

v0.2's four voices become the **first four roles**. Nothing is renamed on disk in
Phase 1; the role is a *semantic label* the generators map to.

| v0.2 voice   | v0.3 role (Phase 1) | Functional group |
|--------------|---------------------|------------------|
| `bass`       | `foundation`        | FOUNDATION       |
| `pad`        | `harmonic-bed`      | HARMONY          |
| `melody`     | `primary-melody`    | FOREGROUND       |
| `percussion` | `mid-rhythm`        | RHYTHM           |

Full role vocabulary (extensible; only the four above are wired in Phase 1, the
rest arrive with their generators in Phases 4–8):

```ts
type MusicalRole =
  | "foundation" | "harmonic-bed" | "harmonic-motion"
  | "primary-melody" | "counterline"
  | "pulse" | "ostinato"
  | "low-rhythm" | "mid-rhythm" | "high-rhythm" | "rhythmic-ornament"
  | "texture" | "transition";
```

**Naming decision:** the existing `VoiceId` (`"pad"|"bass"|"melody"|
"percussion"|"texture"`) is the **renderer routing key** and stays. `MusicalRole`
is the **compositional** label. In Phase 1 they coexist via a fixed map; roles
introduced later that have no dedicated renderer voice route through an existing
`VoiceId` until Phase 8/9 give them their own instrument.

## 3. OrchestrationPlan — internal per-bar orchestration intent

New type (`packages/core/src/orchestration/OrchestrationPlan.ts`), **not**
exported publicly as host API. It is the orchestration analogue of `PhrasePlan`:
pure, deterministic, computed once per bar.

```ts
type Depth = "foreground" | "midground" | "background";

interface OrchestrationPlan {
  readonly activeRoles: readonly MusicalRole[];
  readonly prominence: Partial<Record<MusicalRole, number>>;   // 0..1 mix weight
  readonly activity:   Partial<Record<MusicalRole, number>>;   // 0..1 how busy
  readonly depth:      Partial<Record<MusicalRole, Depth>>;
  readonly focus: MusicalRole;                                 // the ear-lead
  readonly registerBias?: Partial<Record<MusicalRole, number>>;
  readonly ensemble?: string;                                  // named config (Ph.9)
}
```

- `activity` is the **activity budget** made concrete: the director allocates a
  shared ~1.0 pool across active roles, so busier melody ⇒ quieter motion, etc.
  Generators read *their* `activity[role]` instead of re-deriving density from
  raw `state`. This is the single most important behavioural change.
- `depth` + `prominence` drive the renderer's role-aware mix (gain / width /
  filter / reverb). Core describes hierarchy; renderer realizes it.
- `focus` names the one role the listener should follow this phrase; it is
  rotated over long form so the melody is not foregrounded forever.

## 4. OrchestrationDirector — where it sits

New class (`packages/core/src/orchestration/OrchestrationDirector.ts`). It sits
**exactly between `PhraseDirector.plan()` and `Orchestrator.composeBar()`**,
consuming everything already computed:

```
plan(state, phrase, phrasePlan, formState, bar) → OrchestrationPlan
```

It is deterministic and takes a derived RNG (`rng.derive("orchestration/director")`)
only for tie-breaking novelty rules; core arc decisions stay pure.

Responsibilities in Phase 2 (before any new generator exists):

1. **Replace `Arrangement`'s role.** It computes `activeRoles` from energy *and*
   `FormState.section` — so intro/coda are genuinely thinner than climax, not
   just quieter. `Arrangement`'s hysteresis logic is preserved (moved inside the
   director) to avoid flicker.
2. **Allocate the activity budget** across active roles from `phrasePlan`
   (`melodicActivity`, `energy`, `dynamics`) + `state`.
3. **Assign depth + pick focus**, rotating focus across phrases using light
   orchestration memory (see §7).

`ComposerMemory` gains a few fields (recent focus, recent active-role count) to
support the anti-fatigue rules — additive, no breaking change.

## 5. Wiring changes (surgical)

| File | Change |
|------|--------|
| `orchestration/OrchestrationPlan.ts` | **new** — types above. |
| `orchestration/MusicalRole.ts` | **new** — role type + `ROLE_FOR_VOICE`/`VOICE_FOR_ROLE` maps. |
| `orchestration/OrchestrationDirector.ts` | **new** — the director. |
| `orchestration/BarContext.ts` | **add** `readonly orchestration: OrchestrationPlan`. |
| `orchestration/Orchestrator.ts` | replace `arrangement.update(energy)` with `plan.activeRoles` (mapped to voices); pass `orchestration` into each `BarContext`. |
| `engine/LimeEngine.ts` | construct `OrchestrationDirector` (~line 150); call it in `composeBar` after `director.plan(...)`; pass plan into `orchestrator.composeBar`. |
| pad/bass/melody/percussion generators | read `ctx.orchestration.activity[role]` / `depth[role]` instead of (or blended with) raw-state density. **Behaviour-preserving by default** — see §6. |
| `debug/DebugSnapshot.ts` | add `orchestrationPlan`, `focus`, `activeRoles`; keep `activeVoices` derived for back-compat. |
| `style/StylePack.ts` | (Phase 9) new optional `roles` / `ensembles` section; generalize `InstrumentationConfig` from fixed `pad/bass/melody`. **Not touched in Phases 1–3.** |
| `events/MusicalEvent.ts` | (Phase 8/10) optional `expression?` + `role?`; `texture` VoiceId already reserved. **Not touched in Phases 1–3.** |

The renderer (`ToneRenderer`) is untouched through Phase 3 — it still routes by
`event.voice`. Role-aware mixing (depth → gain/width/filter) lands in Phase 3's
renderer pass once core emits `prominence`/`depth`.

## 6. Smallest migration path (the critical constraint)

The brief says: *make the existing four voices respond to orchestration before
adding any generator, and do not destabilize v0.2.* The path:

**Step A — introduce the types, no behaviour change.**
Add `MusicalRole`, `OrchestrationPlan`, `OrchestrationDirector`. Have the
director produce a plan that is **information-equivalent to today**: `activeRoles`
= exactly what `Arrangement` would return, `activity`/`prominence` computed but
initially wired so generators produce byte-identical events. Plumb the plan onto
`BarContext`. **All 118 tests stay green** because generators still read their
old inputs. Snapshot reference-seed output as the regression oracle.

**Step B — move `Arrangement` behind the director.**
`Orchestrator` reads `plan.activeRoles` instead of `arrangement.update()`. The
director *contains* the old gate + hysteresis, so the active-voice set is
identical for identical energy. Tests green.

**Step C — let generators consume the budget.**
One generator at a time, replace raw-`state` density derivation with
`ctx.orchestration.activity[role]`, tuned so the *default* mapping reproduces
current density, then let the director start varying it by focus/depth. Listen
per generator via reference seeds before moving on. This is where the sound
starts changing — intentionally, gradually.

Steps A–B are pure refactor (green-to-green). Step C is the first audible v0.3
change and the validation of the whole architecture, per the brief's Phase 3.

## 7. Orchestration memory (anti-fatigue) — additive

`ComposerMemory` gains (all optional, defaulted):

```
recentFocus: MusicalRole[]        // don't foreground the same role 3 phrases running
recentActiveRoleCount: number[]   // force thinning if full ensemble persists
recentPercussionPhrases: number   // allow a percussion-free phrase periodically
```

These feed the director's focus-rotation and thinning as *probabilities*, not
hard rules, seeded from the orchestration RNG stream so output stays
deterministic per seed.

---

## 8. What this note does NOT change

- Public API (`createLime` / `setState` / `transitionTo`) — unchanged.
- `@lime/core` stays Tone.js-free.
- Determinism: new RNG use is confined to a derived
  `orchestration/director` stream, so harmony/melody streams are unperturbed and
  existing reference seeds still reproduce.
- HarmonyPlanner, FormDirector, MotifGenerator, voice-leading, register
  ownership — all preserved; the director *reads* them, never rewrites them.

---

## 9. Sequencing after this note

1. **Phase 1** — `MusicalRole` + role↔voice maps (Step A types). Green.
2. **Phase 2** — `OrchestrationDirector` + `OrchestrationPlan`, absorb
   `Arrangement`, add depth/focus/budget (Steps A–B). Green.
3. **Phase 3** — generators consume the budget; renderer role-aware mix (Step C).
   First listening checkpoint.
4. Phases 4+ (MotionGenerator, Counterline, harmonic realization, texture,
   instrument abstraction, articulation, long-form arc, demo) follow the brief's
   order, each gated on a listen.

Every phase ends green and listenable. No speculative rewrite.
